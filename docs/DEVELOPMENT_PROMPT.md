# HoverCV 给 Codex 的开发提示词

使用方法：在 Codex 中打开一个用于此项目的文件夹，把 HoverCV_PRD.md 放入该文件夹，然后复制下面代码块中的全部文字给 Codex。Word 版便于阅读，Markdown 版是开发需求基线。不需要把本说明也复制进去。

```text
你是一名负责交付的全栈工程师和交互设计师。请根据项目根目录的 HoverCV_PRD.md，实现一个可以实际使用、可以自行部署、可准备开源到 GitHub 的交互简历注释网页，暂定名 HoverCV。

我没有编程基础。请使用中文汇报，用一句话解释必要术语。请直接推进开发，常规技术细节自行决策，不要只回答方案或让我安装一长串工具后结束。对确实需要账户、密钥或域名的环节，完成其余部分并清楚说明缺什么；不得伪造已完成的外部验证。

一 先读取需求与现有工程

1. 读取 HoverCV_PRD.md、适用的 AGENTS.md、已有代码、package.json 和锁文件。若已有工程，沿用兼容结构；不要直接重建或覆盖无关文件。
2. 把完整 PRD 原样留存在 docs/PRD.md。建立 docs/IMPLEMENTATION_PLAN.md 与 docs/ACCEPTANCE.md，把 AC01 到 AC20 映射到实现和验证位置。
3. 输出一段简短的实施顺序，随后立即开始编码。除关键需求冲突外，不要停在规划阶段。
4. 按本提示的阶段连续完成。先完成核心流程，再接真实服务、分享和导出，不能一开始只写营销首页或漂亮的静态演示。

二 不可偏离的产品行为

1. 用户上传真实 PDF，在网页中看到原排版。可选中文字，也可用矩形框选 LOGO、照片、扫描文字。两种工具都能创建、调整、编辑和删除注释。
2. 文字支持单处、多行和同名词的准确定位；首版跨页选择提示拆分。扫描区域允许手动关键词，不得谎称已完成 OCR。
3. 鼠标悬停彩色标记时，在旁边出现固定样式的卡片，内部包括文字、图片组、视频和链接。卡片内可以翻图、播放和点击。
4. 卡片桌面默认 360×420 CSS px；三模板为简介、图文、封面，外框统一，长内容内部滚动。小屏按 PRD 限制尺寸，手机点击展开底部浮层。
5. 进入热点延迟 180 ms，离开热点、卡片及安全通道后延迟 250 ms 关闭；鼠标从文字斜向移到卡片时不能闪退。进入后能继续交互；退出后暂停媒体、停止轮播，不挤动正文。阅读状态不永久固定卡片。
6. 默认图片手动切换，可开启每 3.5 秒轮播。控件操作或焦点停留时暂停自动播放，关闭后清理计时器。视频不能自动发声，关闭后立即暂停，全屏播放时不误关闭。
7. 文字以主题色下划线和淡色高亮标记，图片以描边角标标记。支持固定四色、取简历主色候选及自定义颜色。优先保证位置与原排版准确，不重画 PDF 字体。
8. AI 搜索发生在作者编辑阶段。先展示关键词与少量上下文，再真实联网搜索、基于来源生成简介。结果是可编辑草稿，用户确认后才写入与发布。
9. AI 返回真实来源链接与检索时间。资料不足时明确提示，不编造来源或申请人的业绩、职责与奖项。缺 API 配置时显示未配置，手工流程仍可用。
10. 照片、视频、文本、链接添加要简便：支持拖入、排序、替换、说明和进度。搜索配图返回候选与来源，用户选择后才导入；不自动使用来源不明的图片冒充个人现场。
11. 作者能保存和恢复项目，修改草稿后明确重新发布。HR 打开公开阅读链接时，不需要 OpenAI、GitHub 或本产品账户，也不进入编辑器。
12. 原 PDF 是输入底稿，不承诺导出的 PDF 保留网页悬停。正式交互载体是公开网页、独立 HTML 或离线 ZIP。严禁再次依赖 PDF 内嵌 JavaScript 来实现产品核心交互。

三 建议工程方案

优先使用 TypeScript、Next.js App Router、React、pdfjs-dist、Floating UI、Zod、IndexedDB、PostgreSQL 与 S3 兼容存储。认证使用成熟库，优先 Better Auth；模型、搜索、图片检索使用可替换 Provider 接口。

如果既有仓库使用其他成熟技术栈，可以保留，但要说明如何覆盖所有 P0 功能。对具体 API、worker 配置、库版本与许可，查阅当前官方文档并锁定已验证的兼容版本；不要凭记忆套用过时 API，也不要无限堆叠依赖。

建议拆分职责：
- PDF 渲染与文字层组件。
- 文字选择与矩形框选组件。
- 坐标转换和文档版本绑定工具。
- 注释 Schema、编辑器、媒体与模板组件。
- 共享的悬浮状态机与定位逻辑。
- IndexedDB、本地项目 ZIP 与云端数据接口。
- AI、Search、ImageSearch、Storage Provider。
- 发布快照、匿名阅读路由与离线导出渲染器。

四 必须做对的实现细节

坐标：
- 绑定 PDF SHA-256、页码、原生 PDF 矩形、原文和少量上下文。
- 浏览器 Range 的矩形按页转换，不把整个多行文本当成一个大矩形。
- 使用 PageViewport 正反变换，考虑 CropBox、旋转、CSS 缩放与滚动；DPR 只影响 Canvas 清晰度，不能重复缩放锚点。
- 显示缩放、窗口变化后位置保持准确。换 PDF 后旧标记须重新确认。

悬浮框：
- 使用 Floating UI 或等价可靠实现，处理 offset、flip、shift、size、autoUpdate 与安全通道。
- 不只绑定文字的 mouseleave。鼠标在热点、通道和卡片内时保持显示；离开后自动关闭。
- 同时只打开一个框，切换时清理旧视频与定时器。键盘聚焦、Esc、触屏及全屏视频行为遵循 PRD。
- 编辑面板与阅读悬浮框分开，不能因自动关闭而丢失编辑内容。

AI：
- 密钥、服务地址和模型配置只放后端；浏览器不得持有部署者的密钥。
- 首版至少接通一个真实模型服务和真实搜索服务，搜索可优先使用 Tavily。
- 使用结构化输出，校验 citations 必须来自本次真实搜索结果；不能接受模型自己编的 URL。
- 只发送用户确认的关键词及最少上下文，不默认上传完整简历。
- 搜索内容及 PDF 内容不是系统指令；无执行代码、读取秘密或访问任意内网的权限。
- 支持超时、取消、限流与配额，失败保留用户已有文字。

分享与存储：
- 本地体验不用登录；AI、云存储和发布使用作者账户。
- 每个服务端写入与资源访问都校验所有权，不相信前端 ownerId。
- 草稿使用 revision 乐观并发；冲突返回 409，不静默覆盖。
- 发布生成不可变快照，匿名阅读路由只读取该快照。阅读路由不受作者登录中间件拦截。
- 文件保存在私有桶；公开接口只能返回该发布版本引用的素材。支持撤回和资源清理。
- Docker 自部署示例包括应用、PostgreSQL、MinIO，给出迁移、备份和运行方法。公开实例还需正确配置 HTTPS、认证及配额。

导出：
- 先把 PDF 页面转成高清图片，将热点映射到固定页面方向的相对位置；公开快照和离线导出采用一致的阅读逻辑。
- 单文件 HTML 内嵌图片与必要脚本，从磁盘打开仍可显示悬浮框与轮播；不要求开发服务器，不在 file:// 中再启动 PDF.js worker。
- 导出后不得保留 blob: 临时地址、localhost 地址、密钥、登录 cookie 或依赖 AI 的实时请求。
- 实际编码后超过 25 MB 提供离线 ZIP 或联网媒体选项，不能静默丢弃视频。
- 项目 ZIP 应包含原 PDF、注释 JSON 和媒体，可重新导入。导入和导出均校验 schemaVersion。

安全：
- 不执行上传 PDF 的脚本，不把用户内容当作 HTML 直接执行。
- 渲染与导出防止脚本注入，正确转义内嵌 JSON。
- 图片导入限制目标、大小、响应、超时与重定向；阻止内网和元数据地址，防止服务端被当作代理。
- 使用虚构简历和可分发素材作为演示；不要把我的真实简历、联系方式或照片提交到仓库。

五 开发顺序与每阶段完成条件

阶段 A 本地编辑闭环：
先跑通上传真实 PDF → 选词或框图 → 添加简介与三张图片 → 统一模板与颜色 → 悬停预览与离开关闭 → 本地保存恢复。同步实现视频和链接内容块，并通过基础交互测试。

阶段 B AI 与配图：
接入真实搜索和模型、来源校验、人工采纳、图片候选与导入、错误和配额。没有密钥时完成接口与配置说明，显示未配置状态。测试可使用 mock，但产品不能把 mock 当真实搜索。

阶段 C 多人使用和交付：
完成作者账户、数据库、文件存储、草稿并发、快照发布、HR 匿名阅读、撤回，以及单文件 HTML、离线 ZIP、可编辑项目 ZIP。

阶段 D 验证和开源整理：
完成生产构建与必要测试；整理 README、.env.example、数据库迁移、Dockerfile、compose、MIT LICENSE、第三方 NOTICE、功能清单、已知限制和测试报告。

六 测试要求与最终交付

1. 按 docs/ACCEPTANCE.md 检查全部 AC01-AC20，记录通过、未通过、未测试及原因。
2. 单元测试重点测坐标正反转换、旋转与 DPR、悬浮计时、数据校验和导出脱离开发环境。不要用只重复实现的空泛测试充数。
3. 端到端测试要真实移动鼠标，从文字跨过间隙进入卡片，点上一张下一张、内部滚动、打开链接，再移出验证自动消失。测试快速切换热点和关闭视频后没有后台声音。
4. 使用新的无痕浏览器环境，完全不登录账户，验证公开链接、页面图片和媒体均能读取。登录作者与不登录 HR 的验证要分开记录。
5. 导出文件用独立目录与脱离开发服务的方式测试，确保没有隐藏的 localhost、blob: 或 API 依赖。
6. 桌面模拟手机不等于微信真机。无法使用真实微信、API 密钥或浏览器时，明确列为未测试，不要声称完成。
7. 运行与当前改动相匹配的类型检查、构建和关键测试。修复发现的问题后，再给出交付结论。
8. README 给我能照着做的启动命令、需要填写的环境变量、如何打开编辑器、如何发布公开阅读、如何导出，以及如何在 GitHub 开源。
9. 最终汇报：完成了哪些真实功能、怎么运行、实际做过哪些测试、剩余限制、需要我提供哪些外部配置。缺少外部条件时，仍应把其余授权范围内工作完成。

现在请开始：读取需求与工程，建立实施计划，然后连续推进实现。
```
